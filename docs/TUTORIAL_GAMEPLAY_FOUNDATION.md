# Gameplay observation and durable lesson foundation

The current runtime supports campaign encounters only. Practice is a reserved tutorial mode; there is no practice encounter or campaign reward path for a practice-tagged snapshot. Do not enable practice until isolated consumables and every reward/clear/offline settlement boundary are implemented. This foundation changes no campaign reward rules.

## Observation

Import observeGameplay from game/GameplayEvents.js. It returns an unsubscribe function. Events are immutable plain data, independent of CombatDiagnostics and its settings. A subscriber cannot stop gameplay by throwing. Delivery occurs in a microtask after the current synchronous gameplay transaction, so a checkpoint flush cannot snapshot a partially assigned command or unscheduled cast. No history is retained when there is no subscriber. Unsubscribe on presenter/controller teardown.

Every envelope includes version:1, type, eventId, profileEpoch, sequence, encounterId, waveId, waveIndex, mode, combatTimeMs, sceneSessionId, tutorial and source. Sources are player (party_leader), ai (actual actor), system and restore. IDs are observation IDs, never diagnostic IDs. The profile epoch and serial are saved; encounter context, pending command IDs, cast IDs and movement evidence survive battle snapshots. Repeated farm waves have separate wave serials. sceneSessionId is transient and changes when the BattleScene is recreated, including snapshot restoration.

tutorial is null outside an active lesson, otherwise {lessonId, checkpointId, attemptId, authorityId}. A command captures it when requested; execution of a prepared command retains that original context even if a new tutorial attempt has begun. A cast captures context at cast start. Player movement retains its command context through arrival and warning avoidance. These origins must never be relabeled as the current lesson at completion. An autonomous cast remains source.kind:ai even when a player order supplies its target. Manual avoidance has its own per-actor tutorial context independently of the system warning-resolution envelope.

The stream is an observation contract, not a debug log or curriculum. Consumers must require the right actor, encounter, wave, cast, command phase and source, and correlate accepted orders with actual effects. Do not complete a damage lesson on assignment, a Move lesson on assignment alone, or an Interrupt lesson on a different/basic cast. Batch 1 adds scene.entered, noncombat selection.changed, adventurer.recruited and party.saved through this same stream; see INTERACTIVE_TUTORIAL.md for producers and committed-fact recovery.

### Recipient semantics

Targeted actor orders report subjectIds for the actors receiving the assignment. That establishes an order, not damage. Coordinated Attack and Lunar Assault choose their living melee/mage role groups independently of UI selection. Their intendedRecipientIds record the group at submission; validRecipientIds and subjectIds report the eligible group at execution. affectedRecipientIds report actors actually assigned by the tactic. affectedTargetIds report enemies whose health or root changed, with per-target damage/rootChanged in effectResults. These are separate concepts: a contributing party member is not the damaged enemy. An applied assignment does not prove positive damage; damage lessons must inspect effectResults.

Immediate party tactics use intendedRecipientIds from submission, validRecipientIds from their production role/eligibility selector, and affectedRecipientIds/subjectIds from actual effect application. Healing or resource restoration with no change can produce an empty affected set. Focus is a party target marker (effectScope:party_target); it has no assigned actor recipients. Area attacks enumerate actual enemy effect results rather than inventing selected-unit recipients.

A queued acceptance has no affected recipients or execution. Rejected/canceled commands have empty affected sets and their real reason. Invalid role groups reject through existing production validation; a reached effect path with no affected recipients reports outcome:no_effect. Each tactic emits one aggregate effect execution; retiring replaced actor orders/movement does not emit extra successful assignments. Superseded metadata is cleared only where production already replaces the corresponding order, and canceled casts carry the explicit player command cause. Buffs that preserve movement retain that movement's own origin.

## Durable controller

TutorialController accepts authored definitions shaped as lessonId -> { firstCheckpoint, checkpoints: { checkpointId: { targetId, allowedInteractions, evidence, next? } } }. evidence requires type and source, with optional command, phase, targetId, castId, waveId, outcome and actorId constraints. These IDs are semantic; no scene objects or screen rectangles are saved. Batch 1 supplies the renderer, registry and input gate described in INTERACTIVE_TUTORIAL.md. No new curriculum is activated from the existing Tutorial menu.

All mutations require a captured authority token. Use capture() for explicit lifecycle operations: begin(lessonId, mode, token), bindEncounter(encounterId, mode, token), exit(skip, token), resume(token), missedOpportunity(reason, token), retry(token), reconcile(token). A successful mutation returns fresh authority. A deferred callback must retain its original token, never recapture current authority to make obsolete work appear current. Ordinary scene changes preserve attemptId; retry and explicit begin issue new attempts. begin is the explicit new-lesson operation, including deliberate re-entry after skip/completion. resume/missedOpportunity cannot reopen terminal lessons.

complete(checkpointId, event, scope.token) requires the actual semantic event and a live scene scope. It validates the authored predicate, player/system source, profile epoch, sequence after scope creation, scene session, encounter/mode, and exact lesson/checkpoint/attempt/authority stamp. AI, queued, stale-scene and obsolete-attempt events cannot complete objectives. Eligible types are scene.entered, adventurer.recruited, party.saved, selection.changed, combat.order.executed, combat.interrupt.succeeded, combat.leaderTap.accepted/resolved, combat.movement.arrived, combat.mechanic.resolved and combat.encounter.finished. Movement requires actual start; warning avoidance requires a matching manual movement context; settlement requires the persisted outcome journal. The future curriculum must add any narrower gameplay predicate it requires. Bare evidence ID strings are no longer accepted. Duplicate completion of the same checkpoint/event/attempt is a no-op without another write.

Every mutation uses an immediate coherent profile flush. It rotates durable authorityId and revokes runtime callback authority before persistence, including a failed write. On failure only the previous tutorial record is restored; no gameplay transaction is undone. Obtain fresh authority to recover after failure. Reentrant transitions are rejected during the synchronous profile flush; rollback never overwrites a state record replaced during persistence. Do not navigate or advance a presenter after an ok:false result. Retry retains prior completed checkpoints and retries only the current opportunity. It does not restart combat, restore HP, reset clears, recruit, consume items or issue rewards.

Lesson checkpoints store version/curriculumVersion, status, lessonId, checkpointId, attemptId, authorityId, mode, encounterId, completed evidence IDs, last outcome, retryReason, semantic targetId and allowedInteractions. Runtime generation, scene session, timers and subscriptions are not saved. Exit pauses; skip retains checkpoint evidence while dismissing the lesson. Resume restores the authored target/interaction set. A bounded journal retains the last 16 encounter outcomes; a bound lesson reconciles its outcome at settlement/load, and reconcile(token) is idempotent. Loading a profile immediately revokes old runtime authority even if the saved attempt is unchanged. There is no migration for obsolete development checkpoint records.

Recruitment retains its separate existing tutorial record and unchanged skip/free-Garrick transaction. The generic controller does not grant ownership or invoke that transaction. The Batch 1 unified Exit dispatcher routes recruitment to its existing skip transaction; it never replaces it with generic exit alone.

### Scene callback ownership

Create scope = controller.scope(scene) after lifecycle mutations/binding. scope.token belongs to that scene session and checkpoint authority. scope.on(emitter, name, callback), scope.timer(delay, callback), scope.observe(callback) and scope.own(cleanup) register transient owned work. scope.guard(callback) guards synchronous callbacks; it does not authorize code after an await. Use scope.defer(operationPromise, apply) to revalidate after an asynchronous operation before a synchronous apply, or validate the original token again before every later deferred write. An already successful recruitment/save/combat transaction remains successful if its presentation continuation becomes stale.

scope.dispose() is idempotent. Scene shutdown/destroy and game hidden/blur remove owned listeners/timers and revoke that scope immediately. Every controller transition disposes all existing scopes. Loading a profile rotates the shared runtime generation and disposes scopes. Callers must acquire a fresh scope after a successful checkpoint change, foreground resume or scene restoration. An old scope cannot block or complete work in the new scene.

Future presenters must reconcile with a fresh lifecycle token on rebind/foreground, then acquire a new scope and live semantic targets. Missing targets/opportunities must wait or enter missedOpportunity/retry, never auto-complete. Batch 1 now implements presentation, target registration, critical-warning suspension and input gating; see INTERACTIVE_TUTORIAL.md. Reward-free practice and the new lesson curriculum remain unimplemented. Device/native Back and real UI lifecycle behavior require their later focused integration validation.
